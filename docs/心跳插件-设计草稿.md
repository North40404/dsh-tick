## 一、已确定的决策

| # | 决策 | 理由 |
| --- | --- | --- |
| D1 | **网络只走 Tailscale** | frp 的 `frps` 在数据通路上且是 TLS 终点；iOS 无 `frpc` |
| D2 | **DSH 本地运行，插件在 DSH 内部** | 走 Cordis service，不需要外部 RPC / Cookie 铸造 |
| D3 | **只适配单一 agent** | 多 agent 引入同频共振与麦权仲裁 |
| D4 | **tick 是决策型调度** | 硬门必须在创建回合之前 |
| D5 | **模型可自主创建 job** | 六道闸兜底（§七） |
| D6 | **tick 是独立通用插件**，不只服务聊天 | 任务可让模型自主调用任何工具/插件（刷 B站、写笔记、自查备份）；「管理员说一句、模型执行一句」不是目标 |
| **D7** | **tick 自己唤醒，且没有事件层** | 领域判断全在模型手里；广播无消费者即死代码 |
| D8 | **设置菜单用 `settings.section`**，每 row 一页 | 插槽已确认存活 |
| D9 | **开关两级**：bundle 启停 + 行级 disable | 去掉内层总开关 |
| D10 | **零代码复用** | 见 §十二 |
| D11 | **不改 meow-memory 任何文件** | 只借结构模式 |
| D12 | **tick 不碰消息**：不认识 message/channel/群聊 | 与桥接零耦合 |
| D13 | **job 稀疏覆盖，四级生效链**（仅行为参数，闸除外） | 降低建 job 的认知负担 |
| D14 | **`mode` 只决定「是否自带预设任务」**：`chat` / `custom` | 保留开箱即用，不引入预设体系 |
| D15 | **单会话绑定**（`boundSessionId` 快照） | 参数可继承，锚点必须快照 |
| D16 | **热切换服务对象 = 冻结旧 job**（`orphaned`） | 旧 `scratch` 依附旧会话 |
| D17 | **`once` 补告知、周期补执行** | 闹钟价值在时刻，巡检价值在动作 |
| D18 | **`origin` 可信，`source` 不可信** | 权限只看可验证的 `origin` |
| D19 | **窗口只约束周期任务**，`once` 豁免 | 免打扰管"主动打搅"，不管"你指定的时刻" |
| D20 | **日历型不自己实现**，引导用 `schedule_create` | 避免重复造 RRULE；代价见 §3.2 |
| D21 | **重要周期任务也豁免活跃窗口** | 重要=不许被规则压掉；打扰的可预见性由"谁设的"决定（用户自设可预见，模型自设受配额约束） |
| D22 | **重要周期任务补告知** | 语义与 once 统一；补告知后**继续排下一轮**（once 补完即终结） |
| D23 | **"错过"计数只统计窗口/上限/预算三类拦截** | 停用与不可达已有独立徽章，重复计数只会让用户困惑 |
| D24 | **全局每日次数闸只统计周期任务** | 一次性任务是你指定的时刻，不该占巡检名额；任务总数另有 `maxJobs` 兜底 |
| D25 | **周期任务最小间隔默认 5 分钟，且不得小于扫描间隔** | 扫描跟不上时更短的间隔没有意义；保存时**拒绝并说明原因**，不自动修正 |
| **D21** | **命名**：包 `dsh-tick`、菜单 `DSH-Tick`、工具 `tick_*` | 见 §9.5 |

### 明确不做

- 多 agent、麦权仲裁
- 端到端加密（Tailscale 已解决）
- 自建 relay
- QQ 式社交机制
- webhook 对外广播
- **事件层**（v1.5 删除）
- 日历型 cadence（用 `schedule_create`）
- 多会话调度
- 任务的模板/预设体系
- 实时状态通道

## 二、定位：tick 与 automation job 的区别

| 能力 | DSH `schedule` | tick |
| --- | --- | --- |
| 固定周期 / 日历规则 | ✅ RRULE（每天 9 点、工作日） | ❌ 引导用 `schedule_create` |
| **随机间隔** | ❌ 确定性表达不了 40~46 分钟 | ✅ |
| **投递前跳过** | ❌ 到点就投递 | ✅ 窗口/空闲/预算/频率，零成本 |
| **预算熔断** | ❌ | ✅ |
| 停机补偿 | 只投最近一次 | ✅ 分级（补告知 / 补执行） |
| **语义** | prompt 以「用户消息」投递 | 明确标注的系统事件 |
| 开箱可用 | ✅ | ❌ 要写 |

> 「语义」这行很关键：用 `schedule` 做"每 40 分钟看一眼"，会话里会出现一堆**像用户说的话**，模型会以为管理员在跟它说话。tick 注入的是带标记的系统事件。

**定位一句话：随机化的、带门控的、语义干净的「给模型一次机会」。**

### 二·补 · 成本模型

```
每天成本 ≈ 触发次数 × 通过率 × 上下文长度
```

三笔成本：① 单次 prefill（可见）② 缓存命中率（隐性）③ **上下文单调增长**（复利——`agent.inject()` 会以 `agent/inbox/spliced` 记入会话）。

对策优先级：两级门 > 降低频率 > 有界 `scratch` > 缓存友好 > 预算熔断。

## 三、总体架构

### 3.1 两条互不相交的路径

```
【消息路径】桥接全权负责，tick 不参与
  客户端消息 → 聚合 → 打标记 → 转述=唤醒 → agent.inject + agent.followup

【tick 路径】tick 全权负责，不认识"消息"
  job 到期 → 硬门 → 渲染模板 → agent.inject + agent.followup
```

结构性质：

1. 免打扰只在 tick 路径上 ⇒「@ 是否穿透免打扰」不存在
2. tick 缺席时聊天完整可用
3. 桥接缺席时 tick 照常工作
4. **tick 之后模型做什么，tick 不管**——可能调桥接读消息、可能调 B站 插件、可能只写条笔记

### 3.2 与 `ctx.schedule` 的分工（含代价）

DSH 已有调度服务（`create/edit/list/view/history/run/deleteInactive`），明确"管理操作不激活会话，只有投递才创建或恢复"。但它是**投递型**：到点直接投 prompt，无投递前钩子。

**分工**：

| 需求 | 谁做 |
| --- | --- |
| 20 分钟后提醒 | tick `once`（相对） |
| 明早 6 点提醒 | tick `once`（绝对） |
| 每 40~46 分钟巡检 | tick `random` |
| **每天 9 点 / 每周一 / 工作日** | `schedule_create` |

**这个切分的代价（明确记录，不粉饰）**：

| 缺口 | 后果 |
| --- | --- |
| 体验分裂 | tick 页看不到日历任务，它在 DSH 自带任务里 |
| 模型要试错 | 先调 tick 被拒，才知道换 `schedule_create` |
| 唤醒语义不一致 | schedule 以用户消息投递，tick 是系统事件 |
| 可靠性不对等 | schedule 无分级补偿 |
| 删除不彻底 | schedule 删除任务**不会撤回已排队的消息** |

**为什么 v1 可以接受**：缺的只有「重复 + 按钟点」这一类，而核心场景是间隔型巡检。若将来它变成高频需求，正确做法是给 tick 加 `calendar` cadence（判别联合加一个分支），**而不是去代管 schedule 的任务**。

> **一条不该越过的界**：一个任务只能有一个主人。缝合只能发生在"展示层链接"，不能发生在"所有权"。

### 3.3 DSH 原语映射

| 需要 | 用哪个 | 备注 |
| --- | --- | --- |
| 定时器 | `ctx.timer.timeout` | 每 job 一个，不共用 |
| 持久化 | `storageDomain.open(spec)` | 不用外部文件 |
| 派生状态 | `ctx.sessionProjections` | 会话日志是唯一真相源 |
| 注入不唤醒 | `agent.inject()` | 留 `agent/inbox/spliced` 记录 |
| 唤醒（三段） | `sessionController.resolveAgent(id)` → `agent.inject()` → `agent.followup()` | 会话未打开时**没有 live Agent**，必须先 resolve/resume；错误码要分别处理（见 §6.10） |
| 空闲判定 | `agent/status`（`idle ⇄ running`） | 等空闲，非跳过 |
| 代理创建日历任务 | `ctx.schedule.create` | **不代建**，只引导 |

> 保留反例：曾计划把计数器放插件外部文件，已否决——会话 fork 后 `lastSpokeAt` 会指向旧会话。

### 3.4 插件形态

- **tick row**（v1 唯一一行）：Host（timer、自检环、硬门、存储、服务、注入）+ Client（设置页 + 任务列表）
- **chat row**（后续）：Host（收发、聚合、唤醒判定、工具）+ Client（设置页）

## 四、TickJob 模型

### 4.1 稀疏覆盖 + 四级生效链（D13）

```
生效值 = job 显式值 ?? 模式预设 ?? 全局策略 ?? 出厂默认
```

> ⚠ 四级链**只作用于行为参数**（`maxPerDay` 等）。
> **安全闸与限额不参与继承**：闸以全局为准且单向——job 只能更严。
> ⚠ **`boundSessionId` 是例外：必须快照**（D15）。

### 4.2 字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | — | `tj_` 前缀 |
| `enabled` | — | 单 job 开关 |
| `cadence` | ✅ | 见 4.3 |
| `scratch` | ✅ | 1~200 字，模型写给未来自己的便条 |
| `importance` | — | `normal`（默认）/ `important` |
| `origin` | — | `admin` / `model`（**可信**，参与权限） |
| `source` | — | `admin-requested` / `self-initiated`（**不可信**，仅审计） |
| `boundSessionId` | ✅ | 创建时快照 |
| `maxPerDay` | — | 默认继承 |
| `guard` | — | `{ waitMaxMs, probability }` |
| `lateToleranceMin` | — | 按 `importance` + cadence 推导 |
| `orphaned` | — | 服务对象切换后置 true，不再触发 |

**无 `window` 字段**：窗口全局唯一（D19）。

### 4.3 cadence 三型四态

```jsonc
{ "type": "once",   "inMinutes": 20 }                       // 相对
{ "type": "once",   "at": "2026-11-17T06:00:00+08:00" }     // 绝对（ISO 8601 带偏移）
{ "type": "fixed",  "everyMinutes": 30 }
{ "type": "random", "minMinutes": 40, "maxMinutes": 46 }
```

- 绝对时间**必须带偏移**；裸时间戳拒绝
- 日历型（每天/工作日）→ 引导用 `schedule_create`

### 4.4 最简 job

```jsonc
{ "cadence": { "type": "random", "minMinutes": 40, "maxMinutes": 46 },
  "scratch": "看看有没有什么想做的；想动手就动手，不想就结束" }
```

## 五、服务契约

### 5.1 服务（`ctx.tick`）

```
create(job)        → 自动填 boundSessionId / origin
update(id, patch)  → patch 语义，"inherit" 恢复继承
cancel(id)
list(filter)       → 含 nextDueAt / lastRun / importance / source
run(id)            → 立即执行一次（reason='manual'，计入日上限）
history(id)        → 含解析后生效值快照
summary()          → 今日次数 / 预算 / 上次扫描 / missed 数量
```

服务需要**暴露给浏览器侧**（任务列表与状态区要读写），这是 Client 半的主要工作量。

### 5.2 为什么没有事件层

| 潜在消费者 | 是否需要事件 |
| --- | --- |
| 桥接 | ❌ 已彻底解耦 |
| UI | ❌ 拉取式，打开页面时拉 + 手动刷新 |
| 日志 | ❌ 内部 `log()` 即可 |
| 未来的第二个消费者 | ⚠️ 纯假设 |

**没有监听者的广播是死代码**，而且会伪装成"这里有个扩展机制"。真出现第二个消费者时再加——那时它才有真实的调用方，契约才有意义。

观测者要什么，查服务；UI 要刷新，重新拉。

### 5.3 硬性语义

1. **迟到**：按 §6.4 分级。
2. **幂等**：`(jobId, dueAt)` 去重——崩溃恢复可能重复触发。
3. **不重试**：只执行一次；需要可靠性的行为由模型在回合内自行处理。
4. **唤醒互斥**：同一 session 同时刻仅一个 `followup()`。
5. **历史存快照**：`history()` 记录每次解析后的生效值，不只记 job id。
6. **改动可见**：改全局策略时 UI 提示「将影响 N 个继承中的 job」。
7. **目标一致性**：触发前校验 `job.boundSessionId === 当前服务对象`，否则跳过并记 `target-mismatch`。

## 六、恢复、补偿与热更新

### 6.1 核心难点

> **进程不在了，时间还在走。**

### 6.2 时间锚点

- 双存 `nextDueAt`（判定权威）+ `lastFiredAt`（审计）
- **random 在排期那一刻抽定并落盘**，重启不重算
- 判定用墙钟；`lastScanAt` 负责跳变检测：负跳 → 全部重锚定 + 告警；正跳超容忍 → 走补偿

### 6.3 自检环

`setTimeout` 的时长与墙钟会脱钩，且脱钩方式依平台而异：

| 情形 | 后果 |
|---|---|
| 系统休眠 | 醒后还要再等一周期，或**醒后集中触发**——两种都可能 |
| 进程挂起（调试器/VM/换出） | 同上，更隐蔽 |
| 时钟跳变 | timer 按单调时长走、判定按墙钟走 → 错位 |
| 循环被长任务阻塞 | 之后集中补发 |

四者从外部看与"正常到期"无法区分。自检环每 `scanIntervalMin`（1 分钟）：

```
delta = now - lastScanAt
├─ delta > scanInterval × 3   → 判定长时间挂起 → 走补偿
├─ delta < 0                  → 时钟倒退 → 全部重锚定 + 告警
└─ 正常                       → 一致性自检：
                                nextDueAt 已过期超过 graceMs 且没有 armed timer → 重排（自愈）
```

**`graceMs`（默认 60 秒）是必须的**：timer 正要触发、还没执行完的那一瞬间，扫描会看到 `nextDueAt` 已过期而判它"该重排"。没有这个宽限就会双触发。

**Token 成本为零**：只读内存与存储，不 inject、不 followup、不写会话。

### 6.4 补偿：重启后周期冻结，闹钟补告知

| cadence | 重启 / 挂起后 | 理由 |
| --- | --- | --- |
| **周期**（含 important） | **冻结**：丢弃错过的那一轮，`next = now + cadence` 重排 | 巡检的价值在"持续"，补一轮昨天的巡检没有意义；"每天关机 → 每天开机补一次"会变成噪音 |
| **`once` normal** | 容忍 **30 分钟**；超限静默丢弃 | 普通闹钟过期就没价值 |
| **`once` important** | 容忍 **30 分钟**；超限进 `missed`，**补一次告知** | 闹钟的价值在时刻：不能执行，但必须让人知道 |

**为什么取消了"重要周期任务 24 小时补偿队列"**：v1.7 之前有这套，但收益（补一轮巡检）小于代价（开机即唤醒的噪音 + 队列复杂度）。定时提醒类的需求应改用 `once` 或官方 `schedule`。

**为什么 `once` 的时间容忍不随重要性变化**：下午两点补一条"吃早上的药"，比不补更有害。所以重要闹钟错过时**不执行原任务，而是告知它错过了**，由模型判断要不要提一句。

**补告知的时机**：

- **不受 30 分钟容忍限制**（否则就没法告知了）
- **受时间窗约束**——窗口外就排队，等窗口开始再唤醒

理由：告知的内容是"已过期"，晚几小时说仍然有意义，且不会造成"现在该吃药"的误导。

**多条 missed 合并**：开机时若有多条，**合并为一次唤醒**（注入里逐条列出），不逐条唤醒。

**`missed` 列表上限 20**：被挤出的条目保留 `reason: queue_full` 标记并在 UI 明示——**不得静默丢弃**（N9）。

**是否重复记录**：同一 job 每日最多产生 1 条 missed。

**名额**：`maxImportantJobs = 3`，**只统计 `origin: model`**。管理员的 important 不占（防模型滥用，不防管理员）。

**模板**：见 §10.3。

### 6.5 关闭与重启

| 事件 | 语义 |
| --- | --- |
| 管理员 disable / 关闭 DSH | **全部停止，不补**。disable 是明确意图 |
| 重新 enable | 重新基准化 `next = now + cadence`，UI 明示"重新计时" |
| 进程重启（崩溃 / 强杀 / 正常重启） | **统一按 §6.4 处理**：周期冻结重排；`once` 按容忍度，重要的补告知 |
| 热重载（HMR） | 同重启；`inflight` 的 run 记"被中断" |

**为什么不再区分「人为关闭」与「意外中断」**：二者在实现上**无法可靠区分**——强杀、断电、系统更新重启都不留痕，靠 shutdown marker 也不稳。既然 §6.4 的补偿策略已经对两类 cadence 分别给了合理结果，这个区分就没有必要了。

> 少一个不可靠的判断，少一类 bug。

### 6.6 单会话绑定

参数可继承，**锚点必须快照**。`scratch` 的语义依附特定会话，绑定漂移会让 job 变成一句无意义的话。

### 6.7 热切换服务对象

切换即冻结，原子顺序：

```
停 timer → 清 missed 队列 → 写入新对象 → 重新扫描排期
```

旧 job 标 `orphaned`（不删、不再触发、可手动迁移）。迁移时**强制重写 `scratch`**（旧语境已不在）。

运行期双检：触发前校验 `boundSessionId` → 不一致则跳过并记 `target-mismatch`。

### 6.8 其他参数热更新

闸在执行期求值，收紧天然立即生效：`minInterval` 提高 → 过密 job 被跳过；`budget` 降低 → 立即熔断；`maxJobs` 降到小于现有 → 不删、只禁新建 + 告警；`scanInterval` 变 → 自检环重启。

### 6.9 存储

| 表 | 内容 |
| --- | --- |
| `jobs` | 定义（`boundSessionId`、`nextDueAt`、`lastFiredAt`、`importance`、`origin`、`source`、`orphaned`） |
| `runs` | 历史（解析后快照、`lateMin`、`reason`、`outcome`） |
| `meta` | `lastScanAt`、`schemaVersion`、服务对象、当日累计、`missed` 列表 |

`schemaVersion` 从第一天就写。

### 6.10 会话失联与归档

DSH 0.2.2 起会归档长期不用的会话。`boundSessionId` 是快照，一旦目标会话被归档：

```
resolveAgent(boundSessionId) → { error: 'session/not-found' }
```

**处理**：不删除 job，标 `unreachable: true` + 记 `lastError`，**UI 顶部告警**（"目标会话不可达，N 个任务暂停中"）。会话恢复后自动清标记并重新排期。

**不自动换会话**：那会让 `scratch` 的语境失效（违反 §6.6 的"锚点必须快照"）。要换由管理员显式操作，且强制重写 `scratch`（与 §6.7 的迁移一致）。

三个错误码的处理：

| 错误码 | 含义 | 处理 |
| --- | --- | --- |
| `session/agent-busy` | agent 有活跃回合 | 走空闲等待，最多 `waitMaxMs` |
| `session/writer-held` | 另一写入者占用 | 同上，短暂等待 |
| `session/not-found` | 会话不存在/已归档 | 标 `unreachable`，不重试 |
| `gateway/internal` | 内部错误 | 记 run 失败，不重试 |

### 6.11 配置热更新

配置**不是**在插件激活时读一次就定死的。订阅 `settings/document-updated`（0.2.x；`settings.watch` 已被移除）刷新内存里的策略副本。

- 闸在每次触发时读**当前**策略值 ⇒ "收紧立即生效"才成立
- `scanIntervalMin` 变化 → 重启自检环
- 读配置要跨版本能力检测：0.1.x 用 `settings.get`，0.2.x 用 `settings.describe()`

## 八、桥接（chat row，本期不展开）

### 9.2 页面结构（拉动式，无实时通道）

### 9.4 模式（D14）——**已废弃，改用按钮**

> **2026-11-21 实现决策**：本节描述的 `mode: custom / chat` **没有实现**，
> 改为任务列表下方一个「新建主动聊天任务」按钮，直接创建一条普通任务
> （`random 60~90 分钟` + 聊天用 scratch），可见可改可删，无隐藏状态。
> 理由与参数见 `dsh-tick-交接.md`。以下保留原始设计，仅作历史参考。

| mode | 行为 |
| --- | --- |
| `custom`（默认） | 不建任何任务 |
| `chat` | 自带一个巡检任务：`random 40~46 分钟`，`scratch` 见下 |

`chat` 预设任务的措辞（34 字）：

> **这次只为聊天：看看有没有想接的话；没话说也可以找管理员聊两句，都不想就结束。**

**三条配套说明：**

1. **假定桥接在场** —— 这条 scratch 默认模型有读消息的工具。只装 tick、不装桥接时，应使用 `custom` 模式自己写 scratch，否则模型会「想看看但无从下手」。
2. **意图限定为聊天** —— 「这次只为聊天：」这个前缀承担全部边界作用。它比「不要做别的事」更有效，因为先给了正面的范围。
3. **其他自主行为另建 job** —— 想让它自主刷 B站、写笔记、自查备份，**不要塞进这条 scratch，而是单独建一个 job**。理由：**一个 job = 一次机会 + 一个意图**；混在一起会导致频率、预算、补偿策略都无法分别设定。

> 边界靠 scratch 是**软约束**，真正的保险是闸：每 job 每日 15 次、全局 100 次、预算熔断 10 元、设置页可一键全停。

**mode 只决定这一件事**：不影响窗口、闸、上限、预算或任何其他参数。切换时停用/启用预设任务，不删除。

## 十、工具面

### 10.1 tick 工具（6 个）

| 工具 | 参数 | 说明 |
| --- | --- | --- |
| `tick_once` | `inMinutes` **或** `at`、`scratch`、`importance?`、`source?` | 一次性 |
| `tick_repeat` | `mode`、`everyMinutes` / `minMinutes`+`maxMinutes`、`scratch`、`importance?`、`source?` | 周期 |
| `tick_list` | `detail?` | 默认精简 |
| `tick_cancel` | `id` | 单个取消 |
| `tick_update` | `id`、`patch` | `"inherit"` 恢复继承 |
| `tick_run` | `id` | 立即执行一次，计入日上限 |

**无 `cancel_all`**：一键全停只在管理员 UI。

`inMinutes` 与 `at` **互斥**；`at` 必须是带偏移的 ISO 8601。

### 10.2 数值与时间严格校验

- schema：`type:"integer"` + `minimum`/`maximum` + `additionalProperties:false`
- 插件内二次校验：`Number.isInteger(x) && min<=x<=max`
- **拒绝时不做宽松解析**（不把 `"20m"` 当 20）——宽松解析会"奖励"错误写法
- 错误返回：`{ ok:false, code:"invalid_number", hint:"..." }`

### 10.3 触发注入契约（不可精简）

| 通道 | 内容 | 精简 |
|---|---|---|
| `tick_list` | id / cadence 摘要 / 下次时间 | ✅ |
| 注入文本 | 固定模板，**英文** | ❌ |

**注入来源必须自证**：注入消息使用**生产者自有的 kind** `{ kind: 'plugin:dsh-tick' }`，**绝不伪装成用户发言**。

> 依据：DSH 0.2.1 起会话格式 v4 **废弃了 `kind: 'plugin'`**，改为要求生产者自有的 kind；写成旧形状会让注入这一步直接失败（任务照常计时，但提示词送不进去）。

**正常触发模板**（英文，与官方 goal / todo / schedule 的注入风格一致）：

```
[Timer] <id>
You scheduled this task at <createdAt>.
Task: <scratch verbatim>
Scheduled: <atLocal> (<atUTC>)
Fired: <firedLocal>, <lateMin> min late          ← omitted when on time
Active hours: outside window                     ← only when outside
-- Act on the task above. If it is no longer meaningful, end the turn without replying.
```

**错过告知模板**（英文）：

```
[Timer] Missed task <id>
Scheduled: <atLocal> (<atUTC>)
Missed by: ~<duration>
Task: <scratch verbatim>
-- This reminder is already overdue; it is not something to do now.
   Mention it if it still matters, otherwise end the turn.
```

多条 missed 合并为一次注入：在 `Missed task` 段落下逐条列出。

**为什么用英文**：官方 goal / todo / schedule 注入给模型的提示词始终是英文（dsh-tick 也默认 `serverPromptLanguage: "en"`）。系统提示与工具提示混用中英文会让模型看到不一致的语气。`scratch` 本身可以是中文，**原样透传**。

### 10.4 scratch 长度上限

`scratch` 是**唯一每次触发都被重复注入的可变字段**，按频率放大：

```
maxPerDay 15 × 200 字 ≈ 3000 字/天/会话
```

| 项 | 限制 |
| --- | --- |
| `scratch` | **1~200 字**（`policy.maxScratchChars`，可调 50~500） |
| 渲染后总长 | ≤ 512 字（防御性） |
| 单位 | **字符** |

超限返回 `scratch_too_long` + hint，**不静默截断**（截断会让说明缺一半，更危险）。

### 10.5 返回值

```jsonc
{ "ok": true, "id": "tj_7f3a",
  "at": 1792838400000,
  "atLocal": "2026-11-17 06:00:00 +08:00",
  "atUTC":   "2026-11-16T22:00:00Z",
  "outsideWindow": true,
  "summary": "将在 06:00 提醒你（该时刻在活跃时段之外，但闹钟不受此限制）" }
```

`outsideWindow` 是**提示不是错误**（`ok` 仍为 true）——避免模型误以为失败而重试。

### 10.6 日历型需求的引导

`tick_*` 识别到"每天/工作日/每月"这类需求时**不代建**，返回：

```jsonc
{ "ok": false, "code": "use_schedule_instead",
  "hint": "日历型需求请用 schedule_create（支持按天/按周规则）。DSH-Tick 只做间隔型。" }
```

**责任归属**：schedule 任务由创建者自己管理。撤回用 `schedule_edit` 的 `action:"delete"`；注意**删除不会撤回已排队的消息**。

### 10.7 工具可见性

`tick_*` 只对**目标会话**的 agent 可见（`agent.ctx` 上 `tools.restrict`，实现时验证）。否则会出现死 job（`boundSessionId` 指向别的会话）。

### 10.8 schema 成本

6 个工具约 600~900 token。缓解：描述 1~2 行、约束交给 schema、稳定前缀可吃 prompt cache、必要时 `tools.restrict` 隐藏。**不要为省 token 合并成 action 单工具。**

### 10.9 业务工具（桥接侧）

| 工具 | 语义 | 约束 |
| --- | --- | --- |
| `send_file(path)` | 发文件给客户端 | 白名单目录、大小上限、发送前确认 |
| `open_app(name)` | 打开应用 | 仅白名单应用名 |
| `ask(prompt)` | 纯对话 | 无副作用 |

**双闸门**：注册期 `tools.restrict()` 隐藏 + 执行期 `tools.guard()` 白名单。**执行点身份校验**（借 SELF_KEY 论证，不借代码）。**审批原样展示**、禁止「总是允许」、超时拒绝。**本地审计**。
